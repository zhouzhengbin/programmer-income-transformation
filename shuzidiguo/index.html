01

三层资产架构模型

核心

在动手建任何文件夹、买任何域名之前，先把这套系统的骨架想清楚。骨架错了，后面越勤奋，将来推倒重来的成本越高。

1.1 一条最重要的原则：单一数据源（Single Source of Truth）

你现在的困惑很大一部分来自"东西散落在很多地方"——脑子里、聊天记录里、桌面上、不同网盘里。这套架构只认一个真相：硬盘上的文件，才是"真"的那一份。网站上显示的、云端跑的、别人下载到的，全部都只是硬盘内容的"投影"或"副本"。这样一来，任何时候硬盘损坏或丢失文件，只要有备份，一切都能原样恢复；任何时候你想清楚"我到底有多少资产"，答案永远在硬盘里，不用去十几个平台后台逐个翻。

1.2 三层容器分别负责什么

🗄️ 硬盘：源仓库层

存放所有源文件、原始素材、脚本代码、账号清单、财务记录、决策日志。它不对外，只对你自己和未来的接手人负责。它的价值标准只有一个：十年后打开还能看懂。

硬盘传承基石

🌐 网站：展示交易层

是硬盘内容的"门面"，负责让陌生人认识你的产品、产生信任、完成购买。它可以随时重建——因为它的所有内容都能从硬盘重新生成，所以网站层可以大胆折腾、试错、换风格。

02

硬盘目录树完整设计

硬盘

建议单独用一块外置硬盘或电脑上单独一个分区，只放这套系统，不要和日常下载、游戏、照片混在一起。九个顶层文件夹，编号即优先级，编号本身就是"如果只能抢救三个文件夹，抢救前三个"的信息。

2.1 顶层九大目录

目录存什么谁会打开它
00_START_HERE给孩子的信、资产总地图、"我不在了请按顺序做"文档、联系人清单家人 / 未来的你
01_ASSETS_资产总账域名清单、账号清单（不含密码）、收入来源清单、资产估值记录你 / 会计 / 家人
02_PRODUCTS_产品库所有python工具/工作流/复杂项目/PDF/图片/视频/图文的源文件你 / 未来的合作者
03_WEBSITE_网站源码网站前后端完整代码，可一键部署你 / 技术接手人
04_AUTOMATION_自动化脚本发布脚本、定价脚本、财务对账、监控告警你 / 未来维护者
05_FINANCE_财务与账户各平台收款账户信息、税务记录、发票你 / 会计 / 家人
06_LEGAL_法律与传承遗嘱相关文件、数字遗产授权书、律师联系方式家人 / 律师
07_LEARNING_经验与知识库决策日志、踩坑记录、市场调研你自己（最大受益人）
08_ARCHIVE_归档废弃产品、旧版本、不再维护但舍不得删的东西基本没人，但别删
⭐
00_START_HERE 不是排面，是真的第一优先级。把它想象成家里那个"如果发生火灾第一个抢救的抽屉"。它体量很小（几份文档），但决定了这套系统在你无法维护时是"资产"还是"一堆没人看得懂的文件"。第11章会详细展开这个文件夹该写什么、怎么写。

2.2 命名规则：让搜索比记忆更可靠

  • 所有顶层目录用两位数字前缀 + 英文关键词 + 中文说明，比如 02_PRODUCTS_产品库——数字前缀保证排序永远正确，英文关键词方便脚本引用，中文说明方便人眼识别。
  • 产品/项目文件夹用创建日期_产品名，比如 20260812_发票自动核对工具，日期在前，任何文件管理器按名称排序即等于按时间排序。
  • 永远不要用"最终版""终极final""真的final2"这类命名——用文件夹层级 + 一个 CHANGELOG.md 记录版本变化，而不是用文件名堆版本号。
  • 每个大文件夹根目录放一个 README.md，一句话说明"这个文件夹是干什么的、里面找什么去哪个子目录"。不确定该怎么写时，就想象你在给一个完全不懂技术、但识字的家人做说明。
示例：README.md 的最低标准

"这个文件夹存放我做的所有付费小工具的源代码。每个工具一个子文件夹，命名规则是『创建日期_工具名』。想看某个工具是干嘛的、怎么用、怎么改，先打开它自己文件夹里的 product_card.md。"

2.3 备份策略：源仓库不能只有一份

硬盘作为"唯一真相"，最大的风险恰恰是"唯一"两个字——硬盘会坏。建议采用简单的3-2-1备份原则：至少3份副本、存在2种不同介质上、其中1份异地存放。

1份工作盘日常读写用的主硬盘/分区
1份本地备份盘用免费的同步工具（如Syncthing）或简单的定时脚本，每天/每周把工作盘完整镜像到另一块物理硬盘
1份云端冷备份选一个便宜的对象存储（如Backblaze B2、又拍云）或干脆用一个加密压缩包上传到网盘，只存关键内容（不含大体积素材），更新频率可以放低到每月一次
⚠️
云端冷备份务必加密后再上传（比如用 7-Zip 加密压缩，或 VeraCrypt 建一个加密容器），因为里面可能包含账号清单、财务记录等敏感信息。加密密码本身要记录在 06_LEGAL 文件夹里说明的取得方式中，而不是明文放在任何网盘上。

04

网站信息架构

网站

网站是硬盘内容对外的门面，核心目标是"陌生人能在90秒内看懂你在卖什么、值不值得信任、怎么付钱"。

4.1 建议的页面结构

首页一句话定位 + 按类型分类的产品入口（工具/工作流/项目/资料/图文）+ 信任要素（案例、评价、联系方式）
产品分类页对应02章的七大类型，每类一个筛选页面，可按价格/热度/更新时间排序
单品详情页（落地页）直接读取该产品的 product_card.md 结构化生成：定位、适合谁、能解决什么、价格、购买按钮
免费/付费分层页用"部分内容免费引流+核心内容付费"的结构，免费内容承接广告/自然流量，付费内容承接转化
关于/信任页你是谁、为什么做这些工具、联系方式——降低陌生用户的购买顾虑
后台内容管理不需要复杂CMS，一个简单的数据库表 + 管理页面，字段直接对应product_card.md的结构即可

4.2 会员/订阅分层建议

层级内容目的
免费部分图文教程、免费小工具、newsletter订阅获取流量与邮件列表，建立信任
单品购买按个买断某个工具/PDF/模板验证单个产品是否有真实付费需求
订阅/会员所有已上架产品的持续访问权 + 优先体验新品在多个产品验证成功后，提升复购和客单价
💡
建议顺序：先做单品买断，跑通至少3-5个有真实成交的产品之后，再上线订阅制。订阅制对信任要求更高，过早推出往往转化很低，反而打击信心。这一点与你已有的《数字产品变现全流程手册》第七章"扩大规模"的建议一致。
05

零成本上线：本地电脑当服务器

技术

这是解决"不想花钱买服务器"的核心方案：让家里的电脑（哪怕是一台闲置的旧笔记本或几百元的迷你主机）扮演服务器角色，通过隧道技术让外网用户访问到，全程不需要公网IP、不需要在路由器上开端口、几乎零成本。

5.1 技术方案总览

🖥️ 本地电脑
Docker 容器运行网站
→
🔒 Cloudflare Tunnel
免费内网穿透
→
🌍 你的域名
全球可访问，自动HTTPS

三个部件缺一不可：Docker把网站打包成"一键可运行"的容器（这一步同时也让03章的03_WEBSITE_网站源码天然具备了"随时能在任何机器上跑起来"的能力，为第7章的云端迁移埋下伏笔）；Cloudflare Tunnel是免费的隧道服务，让处于家庭网络NAT之后、没有公网IP的电脑也能被外网访问，且自动提供HTTPS证书；域名则通过一条CNAME记录指向这条隧道。

5.2 具体搭建步骤

准备一台常开机的设备闲置笔记本、二手迷你主机（如Intel N100机型，二手价约几百元，功耗低到可以24小时开着）、或树莓派均可，装好Docker与Docker Compose
把网站写成docker-compose.yml放在硬盘的 03_WEBSITE_网站源码 目录下，一条命令 docker compose up -d 即可启动全部服务（网站程序+数据库）
注册Cloudflare账号并接入你的域名Cloudflare是免费的CDN/DNS服务商，接入域名后可以使用它的Tunnel功能
安装cloudflared并创建隧道在本地电脑上运行cloudflared，把隧道指向本地Docker容器监听的端口，Cloudflare会自动处理HTTPS证书
设置开机自启与自动重启Docker容器设置 restart: always，操作系统层面设置Docker服务和cloudflared开机自启，保证断电重启后自动恢复
接入免费的可用性监控用UptimeRobot等免费服务，每5分钟探测一次网站是否在线，掉线时邮件/微信提醒你
⚠️
本地方案的现实局限，要提前接受：家庭网络的稳定性、带宽、以及"家里停电/路由器重启"的意外情况，决定了它无法做到云服务器级别的99.9%可用性。适合的阶段是产品验证期、访问量不大的阶段——这恰恰和你目前"先想清楚框架、还没大规模投入"的状态完全匹配。等某个产品流量明显起来、或者需要对外接单/被商业伙伴依赖时，第7章会讲清楚怎么无缝搬到云端。

提升稳定性的低成本手段

  • 给电脑配一个几十元的小型UPS（不间断电源），短时停电不掉线
  • 用有线网络代替WiFi，减少不稳定因素
  • 路由器设置为电脑分配固定内网IP，避免IP漂移导致服务异常
  • 准备一个"电脑没开"时展示的临时静态页面，托管在Cloudflare Pages（免费），作为兜底
06

域名选购指南：稳定 + 高性价比

网站

域名是这套系统里少数需要"长期持有、不轻易更换"的资产，选错注册商最常见的坑是"首年低价、次年暴涨"，稳定性比一次性便宜更重要。

6.1 注册商对比

注册商特点适合场景
Cloudflare Registrar按批发成本价收费，不加价，没有"首年低价次年暴涨"套路，且与Tunnel/CDN天然集成长期持有的主力域名，强烈推荐配合第5章方案使用
Porkbun界面友好、价格常年在第一梯队、支持免费WHOIS隐私保护作为备选或用于注册多个变体域名
Namesilo老牌稳定、续费价格波动小、同样自带免费隐私保护喜欢"一次设置不用管"的用户
阿里云 / 腾讯云国内平台购买+备案一体化更方便，需要面向国内用户走.cn域名或需要ICP备案时更适合国内独立站/需要备案的场景
🚩
不建议把域名注册在首年促销价格极低、但续费价格成倍上涨的平台（这是不少大型域名商的常见套路）。判断标准很简单：注册前直接搜"域名商名+续费价格"，如果续费价格是首年的3倍以上，慎选。

6.2 后缀与购买策略

  • 面向国际用户优先 .com，其次 .io / .co；面向国内用户可以 .com 搭配 .cn
  • 不需要一开始就买齐所有后缀变体，先用一个主域名跑通验证，等某个品牌名被验证有价值后，再考虑买齐防止别人抢注
  • 开启域名自动续费 + WHOIS隐私保护（大多数上述注册商免费提供），避免忘记续费导致域名过期被抢注
  • 域名到期提醒设置双重保险：注册商邮件提醒 + 自己在日历上手动加一条提前30天的提醒
🔑
域名的注册商账号本身要在第11章"传承系统"里被明确记录——域名一旦过期被抢注，几乎无法追回。这是整套资产里最脆弱的单点，一定要在传承文档里给予最高优先级说明。

未来云端迁移路径

网站

因为第5章已经把网站容器化（Docker Compose），从本地电脑搬到云服务器时，理论上不需要重写任何代码，只是"换一个地方运行同一份容器"。

7.1 什么信号说明该升级到云服务器了

  • 某个产品的访问量开始让本地网络明显卡顿，或监控工具报告的掉线次数明显增多
  • 开始有商业伙伴/广告投放依赖网站的稳定在线，掉线造成的损失开始大于服务器成本
  • 需要7x24小时运行需要更高算力的自动化任务（比如定时爬虫、批量视频处理）

7.2 迁移步骤

选一台性价比高的云服务器入门阶段选最低配（1核1G或2核2G即可），不需要一步到位买贵的
在云服务器上安装Docker，拉取硬盘里的网站源码直接用03章的 03_WEBSITE_网站源码 目录，运行同一条 docker compose up -d
迁移数据库/文件数据用数据库自带的导出导入工具，把本地容器里的数据同步到云端容器
先用测试域名/子域名验证云端版本运行正常比如先用 test.你的域名.com 指向新服务器，确认无误后再切正式域名
把DNS记录从Cloudflare Tunnel切换为直接指向云服务器IP切换瞬间可能有几分钟DNS生效延迟，建议选低流量时段操作
本地电脑保留为备用/开发环境不必关停，可以继续作为测试新功能的场所，云端只跑正式版本
✅
这套"本地先验证、云端后规模化"的路径，本质上和你在《数字产品变现全流程手册》里"先小范围测试、验证后再扩大投放"的逻辑完全一致——只是把这个原则从"营销动作"延伸到了"技术基建"上。不要在还没验证产品价值时就为可能不需要的规模提前买单。

自动化三阶段路线

自动化

自动化的前提永远是"已验证有效的动作"，而不是"还没验证过的猜测"——这是贯穿本手册与你已有两份手册的共同原则。以下把整个自动化历程拆成三个阶段，避免一上来就想做全自动，反而因为太复杂而卡住不动。

阶段一：全手动验证期

所有发布、定价、回复消息都手动完成。目的是先确认某个产品/渠道组合真的有人愿意付费，同时在07_LEARNING里记录每一步的手感和数据。

人工为主

阶段二：半自动化期

把已验证有效的重复动作脚本化：例如用脚本批量生成不同渠道的产品详情文案、自动生成销售数据周报、定时把各平台流水抓取汇总到05_FINANCE。但涉及"钱"和"决策"的环节（比如是否降价、是否下架）仍由人工确认。

脚本辅助

阶段三：编排自动化期

用n8n等工作流工具，把"新产品完成→自动生成落地页→自动发布到多渠道→自动同步库存/价格→自动汇总数据"串成一条流水线，人工只负责创作新内容和审核关键节点。

工作流编排

10.1 建议的自动化工具栈

用途推荐工具备注

给孩子的传承系统

传承 · 核心

这是整份手册里最不一样的一章。前面十章教的是"怎么把事情做起来"，这一章要回答的问题是——如果有一天你不在了，一个也许完全不懂技术、正处在悲伤中的家人，怎么才能在不求助任何人的情况下，看懂并接手这一切。这不是悲观，而是一种对家人最踏实的爱。

11.1 设计原则：写给"不懂技术、心情沉重"的读者

  • 语言要简单到不需要任何背景知识——不用"部署""容器""DNS"这类术语，改用"怎么让网站重新打开"这种大白话
  • 信息分层：最紧急、最重要的放在最前面一页纸；细节放在后面，需要时再翻
  • 不在这份文档里写任何真实密码——只写"密码在哪里、怎么合法取得"，密码本身交给专门的密码管理器和法律流程去保管
  • 定期更新——建议每季度花15分钟检查一次这份文档是否还准确，账号变了、密码管理方式变了都要同步更新

11.2 00_START_HERE 文件夹应该放的五份文件

① 给孩子的一封信.pdf

不需要写得多正式，就是你想对孩子说的话——为什么做这些东西、希望这些收入怎么被使用、对Ta未来的期待。这份文件的作用不是"技术交接"，是情感锚点，让后面几份冷冰冰的操作文档有了温度和意义。

② 资产总地图（一页纸）

一张表，列出：我有哪些网站/域名、哪些产品在哪些平台上架、钱主要从哪几个渠道进来、目前每月大概能产生多少收入。目的是让家人5分钟内对"这套系统值多少钱、复不复杂"有一个整体判断，决定是要继续经营、请人托管、还是逐步关停变现。

③ 如果我不在了_请按顺序做.md

用类似本手册的"step-list"风格，写清楚最开始几步该做什么——比如"第一步：联系xx律师，电话在联系人清单里""第二步：域名续费日期都在资产总地图里，先确认没有临近到期的""第三步：如果决定继续经营，联系xx（如果有信任的合作者/技术顾问）"。不追求覆盖所有情况，只求把最初、最容易出错的几步说清楚。

④ 联系人清单.md

律师、会计/税务顾问、域名注册商客服方式、如果有信任的技术合作者也列上，附上各自能帮上什么忙的一句话说明。

⑤ 密码管理器access说明.md

说明你使用的密码管理器是什么（建议用支持"紧急访问/继承人"功能的产品，比如支持Emergency Access的密码管理工具），以及依照法律程序（遗嘱、公证）可以怎样合法取得访问权限——这份文件本身不包含任何真实密码，只是一张"钥匙在哪个保险箱、保险箱怎么合法打开"的说明图。

11.3 与正式法律文件的配合（06_LEGAL目录）

数字资产的传承光靠一份文档并不具备法律效力，建议尽快、且以此为契机，完成以下两件事，并把结果的说明（非敏感内容）也放进06_LEGAL：

咨询一次本地律师，完成或更新遗嘱明确写入"数字资产"条款，包括域名、网站、各平台账号及其收入的处置方式——不同地区对数字资产的继承认定方式不同，务必以本地专业意见为准，本手册不构成法律建议
为密码管理器设置正式的"紧急联系人/继承人"机制大多数主流密码管理器都提供这项功能，可以设置延迟授权（比如申请后30天无异议自动开放访问），既保证你在世时的安全，也保证万一发生意外时家人不会被完全锁在门外
💛
这一章看起来是九个阶段里最"不像商业规划"的一章，但恰恰是你最初提出的核心诉求。把它做好，不需要花钱、也不需要太多时间——真正需要的只是一次认真、诚实的自我梳理。建议读完这一章后，先花一个周末，把00_START_HERE的五份文件写出初稿，哪怕不完美，有胜于无。

总检查清单

十二章逐一自查，一句话标准
?

常见问题

我现在完全没有任何产品，是不是应该先建好整套系统再开始做产品？+

不建议。第1周只需要把9大顶层目录建好、写好00_START_HERE的初稿即可（合计不超过半天），剩下的目录会随着你做第一个产品自然填充起来。这套框架的目的是"让你在做事的同时不迷路"，而不是"做事之前先花几周搭系统"。

本地电脑当服务器，家里网络运营商会不会有问题（比如封禁）？+

正常的家庭宽带套餐本身不禁止你运行个人网站，但要注意两点：一是很多家庭宽带是动态IP甚至运营商级NAT（没有独立公网IP），这正是本手册选择Cloudflare Tunnel方案的原因——它完全不需要公网IP；二是如果网站访问量变得很大、接近商用规模，建议提前评估当地宽带套餐条款，避免因为流量或性质问题被限速或调整。

孩子还小，现在写"给孩子的传承系统"是不是太早了？+

不早。这份文档的价值不取决于孩子现在几岁，而取决于系统本身是否存在，以及是否有人能理解它——传承文档写的是给"未来任何一个需要接手的人"看的，可能是长大后的孩子，也可能是你的配偶或其他信任的家人，越早建立、越早养成季度更新的习惯，未来任何时候需要用到它时越不会措手不及。

密码到底应该存在哪里？+

建议使用一款支持"紧急访问/继承人"机制的密码管理器（大多数主流产品都有），日常密码全部存在里面，只在遗嘱和联系人清单里说明"怎么通过合法流程取得访问权"，而不是把明文密码写进任何硬盘文档、聊天记录或云端笔记里，这是整套系统里唯一一处坚持"不落地成文件"的信息。

这套硬盘框架和我以前随手建的文件夹差别大吗，需要把旧文件全部推倒重来吗？+

不需要全部推倒重来。建议新建这9个顶层目录后，用一到两周时间，把旧文件按内容性质分批"搬家"归位即可，搬的过程本身也是一次很好的资产盘点。暂时分类不清楚的文件，先扔进08_ARCHIVE_归档，不要因为"一步到位分类干净"而拖延了整体框架的建立。

本地Docker方案会不会太"技术"，我完全不懂编程能搞定吗？+

Docker和Cloudflare Tunnel的安装本身有大量图形化教程，跟着官方文档一步步操作，通常一两个小时可以跑通第一次。如果确实卡住，也可以把这部分作为"愿意花一点点钱外包的第一个环节"——花几十到一二百元请人帮你搭一次初始环境，之后日常的启动/重启只需要记住几条固定命令即可，不需要持续懂编程。

要不要现在就买多个域名把品牌名占全？+

不建议。参考06章的建议，先用一个主域名验证产品和品牌名是否真的跑得通，被验证有价值之后再考虑买齐后缀变体防止抢注。过早在多个域名上花钱，属于在验证之前为可能不需要的规模买单。
